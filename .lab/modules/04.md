## Module 4 — Write your first consumer

**Goal:** decode the stream yourself, in a language of your choosing, without
being told what is in it.

This is the last Foundation module, and the first where you build something
rather than edit something.

### Your task

Write a consumer. Any language, any Kafka client, any protobuf library.

It has to read the telemetry back out of Kafka and write
**`.lab/my-consumer.json`**:

```json
{
  "sessionIdentifier": "Sandbourne Park - yourhandle - reference - 14:02:11",
  "channels": [
    { "identifier": "Speed:SandbourneGT3", "units": "m/s", "samples": 4278 }
  ],
  "lapMarkers": 3
}
```

The full contract, the topic names, where the schema lives and the traps are all
in **[`my-consumer/README.md`](my-consumer/README.md)**. Start there.

The validator runs `bash my-consumer/run.sh` from the repository root. Make that
script do whatever your language needs.

### The rules

- **Read the reference consumer in [`consumer/`](consumer/). Do not call it.**
  It is there to be learned from — it is the same job, done in Node.
- **Do not hardcode anything.** The validator invents a new channel on every
  run, with a name and units it makes up, and varies the number of laps. A
  consumer that assumes eleven channels, or has the unit strings baked in, will
  fail — and that is the entire point of the exercise.

### What you are actually being asked to prove

That you can take a stream of bytes you have never seen, and recover from it
what the channels are, what they mean, how many samples each carries, and where
the laps fall — **using only what the stream itself tells you**.

That is the difference this platform exists to make. On a bare topic, all four
of those facts live somewhere else: a schema registry, a wiki, a naming
convention, someone's memory. Here they arrive with the data.

Your consumer will be graded against what the **producer** recorded sending, not
against ours. Two implementations can share a misunderstanding and agree with
each other while both being wrong.

### Understand it

Before you move on, find out why this works the way it does — the real
protobuf definitions, the failure it prevents, and how to apply it to your
own systems:

```bash
lab explain
```

### Check it, then submit it

Run the validator here first. It is the *same* code the bot runs, it takes
seconds, and nothing is pushed:

```bash
lab check
```

When it passes:

```bash
lab submit
```

That branches, commits, pushes and opens the pull request against `main` in your
own repository. The bot runs the whole pipeline again on a clean machine,
comments with what happened, and on a pass advances your README and merges.
